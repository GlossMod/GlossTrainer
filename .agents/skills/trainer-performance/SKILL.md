# 修改器性能优化

围绕游戏线程的实际热点减少每帧工作量，保留功能契约、状态恢复及用户操作反馈。先区分持续基础开销、周期尖峰和特定页面开销，再选择优化方式。

## 定位范围与证据

- 从仓库根目录读取 `AGENTS.md`，确定游戏模块与请求范围。分析或评审任务只读执行；实现任务只修改相关游戏模块。不要把一个游戏的地址、偏移、对象布局或缓存有效期直接套到另一个游戏。
- 分析性能 PR 时固定 base/head 提交，比较实际代码与测试，再读取描述。来源结论、源码推断和本次复测分开表述。
- 复用 PR #1 的经验或调查 PBZ 同类热点时，按需读取 [PR #1 案例与源码入口](references/pr-1-case-study.md)。该案例的倍数和参数不是新任务的验收目标。

## 先确定计时边界

从 Hook 入口画出调用链，标出原游戏函数、事件名称过滤、上下文读取、修改器 Tick、状态查询、请求执行、物品维护和渲染线程。检查计时器之外是否还有重复工作；也检查 Hook 是否在每个事件、每个 Actor 或每次 Present 上触发。

`Tick`、名为 `frame` 的自定义区段、完整游戏帧和实际呈现 FPS 是不同指标。查看计时代码后才能解释名称；墙钟计时包含等待与线程抢占，不能直接当作 CPU 执行时间。嵌套区段不可直接相加。

优先取得与反馈对应的场景：菜单关闭且全部功能关闭、开启相关功能、打开问题页面，以及会话切换或冷缓存加载。记录构建配置、提交或产物哈希、游戏版本、场景、缓存状态、采样时长和调用次数。缺少游戏或原始日志时，继续源码定位及可运行的本地验证，明确未完成的实机证据。

新增测量应足够轻量：聚合调用次数、总耗时、最大值和超预算次数，必要时采集分位数或短期采样。把统计格式化与磁盘输出移到热路径之外；计时器自身的日志输出可能不在该区段计时内，需要另行核对。

## 按热点选择改法

| 热点信号 | 优先考虑 | 正确性条件 |
| --- | --- | --- |
| 全关仍慢，反复验证对象或函数地址 | 统计 `VirtualQuery` 次数和耗时；稳定主模块可用初始化时捕获的 PE 可执行节范围作快路径 | PE 标记不等同当前页面保护；明确模块及保护稳定性假设。未知或模块外地址保留查询，避免把所有地址视为有效 |
| 反射或名称查找重复遍历 | 缓存字段/函数结果；短期缓存未命中；追加型名称池记录完整扫描进度 | 使用对象身份与会话信息失效，命中仍做必要校验；查找失败可过期重试，读取故障不能记成有效的完整未命中 |
| 定时出现长帧 | 将整批状态回读、文本格式化等拆到多帧；无人查看时降低频率 | 执行用户请求后及时回读；会话变化丢弃未完成结果。说明状态新鲜度代价，不对依赖实时维护的功能一律降频 |
| 游戏线程与渲染线程互相等待 | 空闲原子提示提前返回；缩短临界区；模型版本号加不可变共享快照 | 业务状态仍受原同步机制保护；审查所有修改入口、发布顺序和读取竞态，保证不会遗漏请求或界面更新 |
| 每帧遍历物品、排序或拼接搜索文本 | 按发布版本、数据身份及查询条件缓存派生结果，静态目录只初始化一次 | 失效条件包含会话、语言、Debug/可见性规则、搜索与分类；缓存指针必须持有对应数据的生命周期 |
| 加载或保存时卡顿 | 将序列化与写盘移到后台；游戏线程只交付拥有所有权的数据快照 | UObject 访问和引擎调用仍留在允许线程；处理较旧保存覆盖新保存、失败与模块退出生命周期 |

先处理高频且单次昂贵的基础调用，再处理重复扫描和集中批次，最后减少字符串复制、格式化等剩余开销。以上是调查优先级，不能代替测量；没有逐项对照时，不给各改动编造贡献百分比。

## 实现时保留的语义

- 不能通过删除对象有效性、函数签名、布局契约或执行后校验来获得性能数字。将不变部分与动态校验分层，并说明快路径依赖的假设。
- 对象地址可复用；仅地址相同不能证明身份相同。根据现有引擎证据组合会话、对象索引/序列号、名称和所有者关系，重新绑定时清理缓存及旧批次。
- 负缓存避免永久屏蔽迟加载类型；增量扫描只适合追加且已有项稳定的数据。数组收缩、池重置、槽位复用分别需要重扫或失效策略。
- 帧预算是批次间的让出条件，不能抢占单次同步引擎调用。按时间和条目数约束批次时，也记录单次调用的最坏开销。
- 版本号需要覆盖所有影响快照的写入。先读版本再复制快照，允许并发变化在下一帧补取，避免把旧快照标记为已覆盖新版本。
- 后台化只迁移独立工作；不要把游戏逻辑整体移入工作线程。对异步任务明确数据所有权、任务顺序与关闭/卸载行为。
- 保留保存开关恢复、会话切换、快捷键、用户操作后的即时反馈。局部优化不隐含安装、注入、发布或修改游戏文件的授权。

## 验证与交付

对受影响缓存与调度行为做有意义的回归验证：对象身份变化、未命中过期、会话重置、中途执行请求、空闲后提交、模型更新与快照失效；异步写入则检查旧任务不能覆盖新数据。按仓库要求运行受影响的 Debug/Release 构建与测试，读取实际 `xmake.lua` 获取目标，避免假定所有游戏使用同名测试。

能实机采样时，在可比场景下对比优化前后。均值反映持续负担，最大值和分位数反映卡顿；均值下降不能证明尾部卡顿消失。仅合并不重叠且计时口径一致的窗口，平均值按调用次数加权。单元测试验证语义，图形宿主验证覆盖层路径，两者都不能代替游戏内性能与功能验证。

生成的日志、结果 JSON、截图和基准放到仓库根 `output/<任务>-<YYYYMMDD>/`。需要记录游戏验证结论时，写入 `<Game>/docs/verification.md` 并链接原始证据；不要把原始输出放进 `docs/`。

交付说明应包含已定位热点与调用链、修改后的行为及缓存/调度边界、前后计时范围、已运行验证和仍缺少的证据。耗时倍数为 `before / after`，下降比例为 `1 - after / before`；不将局部耗时倍数宣称为 FPS 提升，不把合成基准宣称为游戏实测。
